# 性能冲刺收尾报告：first_myself_site（2026-09-30）

## 结论

本轮修复的重点不是继续堆优化，而是把曾经声称上线、实际在冲突合并后丢失或证据不足的行为重新交付并可验证：

1. 文章详情的 metadata 与页面渲染共享一次请求级文章查询；合集和相关文章继续复用现有 viewer-aware 查询边界。
2. 匿名公开内容使用共享缓存；任何登录态都直查。底层匿名查询固定 public/published 条件，并显式 `overrideAccess: false`。
3. 文章页 10 个站内 `Link` JSX 位置关闭自动 prefetch，但真实点击仍可导航。
4. public/published 内容撤回或删除时，缓存失效失败会让 by-ID 写操作回滚；普通更新失败只告警并由 TTL 收敛。由于 Payload bulk 路径不能保证相同回滚语义，Blog 与 BlogSeries 后台关闭 bulk edit/delete。
5. 测量升级为 fail-closed 的 `perf-v2`，并加入只读检查的性能棘轮。

实验室四个完整可比批次全部通过冻结门槛；文章页旧基线因取消的重复预取请求为 0/15 完整，候选在桌面和手机均为 15/15 完整。不能据此伪造文章页提升百分比。

## 为什么需要收尾

- 原性能实验提交 `f4cca80` 曾包含文章请求去重、缓存接入和文章页 prefetch 控制。
- 后续冲突合并后的最终提交 `79c0a417` 没有保留文章页的全部行为，旧实验数字不能证明最终上线代码。
- 原 `perf-v1` 会漏计慢资源、过滤失败样本并继续计算分位数，旧请求/字节数字不是完整账本。
- 原报告把 JSX 位置数、运行时链接数、网络请求数和服务端渲染次数混为一谈。

因此本报告明确撤回这些旧说法：

- “27 个链接全部上线”；
- “每次浏览少执行 11–17 个完整 SSR”；
- “完整请求/字节下降已证实”；
- “缓存命中签名存在”；
- “访客内容最多陈旧 60 秒”可作为撤回保证。

旧数据保留为 `perf-v1` 历史材料，不再作为当前验收结果。

## 当前实现

### 文章读取和权限

- `app/(main)/blog/[slug]/page.tsx` 使用模块级 React `cache()`；参数只有解码后的 slug，viewer 在 helper 内读取，避免把可伪造身份放进缓存 key。
- `generateMetadata` 与页面组件共享 helper；页面继续按返回的 viewer 判断管理员能力。
- 匿名 Blog 列表/单篇缓存底层查询同时保留 public/published where 和 Payload access control。

### 失效与撤回

- Blog 普通公开更新：失效失败告警，TTL 仍可收敛。
- Blog 从 public/published 变为 private/draft，以及公开 Blog 删除：失效失败向外抛出，由 by-ID 更新/删除事务回滚。
- BlogSeries 从 published 变为 draft，以及 published series 删除：同样 fail closed。
- 数据库集成测试在隔离 PostgreSQL 中证明 public→private by-ID 更新在失效异常时回滚。

生产内容写入和撤回验证尚未授权，部署后只能进行只读检查并标记 `not_verified`。

### prefetch 控制

本轮恢复的是文章详情文件里的 10 个 JSX 位置：返回列表、合集徽标、合集目录项、合集介绍、查看合集、上一篇、下一篇、合集末尾返回博客、全部文章、相关文章项。它们是源代码位置，不等于固定数量的运行时链接或请求。

## 生产状态与限制

生产结果只有在 PR 合并、GitHub Actions 部署完成、部署身份核对且稳定窗口满足后才能追加。生产没有可信的 perf-v2 同协议前测时，只报告绝对值，不计算提升百分比。

本轮没有生产内容写入授权，因此不会通过修改真实文章验证缓存刷新，也不会执行 public→private/draft 撤回；这两项生产验证记为 `not_verified`。本地单元与 PostgreSQL 集成证据不能冒充生产证据。

## 回滚

本轮无 schema migration。若只读生产 smoke、身份核对或性能门槛失败，按现有 GitHub Actions / 镜像链路回滚应用；代码层可 revert 本轮 PR。若出现匿名读取 private/draft、关键页面/SEO/角色门禁/Agent/合集退化，立即停止放行。

## 后续边界
