# 实验日志

> 每次改动一条：假设 → 最小改动 → 护栏 → 测量 → 保留/回退。
> 过程测量为「重建后单版本 bench」（15 次 fast4g）；最终结论以基线 commit 与最终版本的同时段 A/B 配对测为准。

## 实验 #1：文章查询请求级去重

- **假设**：`generateMetadata` 与页面组件对同一 slug 各查一次库（Local API find 一次约 15–25ms）；用 React `cache()` 去重后，文章页服务端 TTFB 应降 15–25ms，fast4g 能用 p75 同步下移。
- **改动**：`app/(main)/blog/[slug]/page.tsx` 抽出 `findPost = cache(...)`，两处共用。
- **护栏**：tsc ✓；golden check ✓（可见文本/正文 HTML/SEO/计数/截图/sitemap 逐项一致）。期间发现并修复了护栏自身的两个问题：playwright JS 把字符串当表达式求值（bench.mjs 的 COLLECT_JS 改 IIFE、waitForFunction 参数位）；整页截图须等 networkidle+fonts 才跨构建稳定（golden.mjs 已加固并重采参照）。
- **测量**（重建后单版本 15 次 fast4g）：文章能用 p75 **319.8 → 266.4ms（-16.7%）**，p50 292→261，p95 438→296；请求数 26 不变，字节 +68B；首页/列表无变化（248.6 / 245.2，在上限内）。
- **结论**：**保留**。归因：metadata 与页面两次串行 find 合并为一次，首字节前的等待少了一整段查询。另发现基线记录的 203ms TTFB 含首次请求预热成分，稳态服务端耗时约 17–30ms；fast4g 下「能用」时间的大头是 HTML 文档传输与非流式渲染，不是数据库。

## 实验 #2：文章正文 Suspense 流式渲染

- **假设**：正文一体渲染完才发首字节；包进 `Suspense` 后标题区先流出、正文流式推送，预计能用 p75 再降 50–80ms。
- **改动**：正文容器内 `<Suspense fallback={null}>` 包裹 `MarkdownArticle`。
- **护栏**：proseHTML 差异经查证仅为 React 边界注释（剥除后逐字节一致）；护栏采集已加归一化。
- **测量**：**能用 p75 恶化到 576.2ms**（572-582 极窄分布）。诊断：正文并非渐进到达——200/2000/8000 字符在 508ms 同帧齐现，即大体积流式 Suspense 段的服务端渲染开销反而增加了 ~240ms。
- **结论**：**回退**。教训：流式对小段慢查询有效，对一次性大块同步渲染（Markdown→React 树）是负资产。

## 实验 #3：内链 prefetch 治理（用户已批准的 C 方案）

- **假设**：所有内链默认 prefetch，而这些路由全是动态渲染——每次页面浏览触发 4-17 次额外的完整 SSR+DB 查询；单进程生产环境（线上 TTFB 0.68-2.53s 且波动巨大）下这些负载互相排队。关掉后线上应显著回落，实验室请求数应大幅下降。
- **改动**：`Navbar.tsx`、首页、博客列表、文章页共 27 个 `<Link>` 统一加 `prefetch={false}`。
- **护栏**：lint ✓、golden check 全绿（DOM 与截图不变——prefetch 不改页面本身）。
- **测量**（15 次 fast4g）：首页能用 p75 263.1→**240.4**，请求数 27→**10**，字节 188.5→171.6KB；列表 246.6→**238.8**，请求 25→**10**；文章 ~284→281（噪声内），请求 26→**16**，字节→270.8KB。棘轮 9 项全部下调锁死。
- **结论**：**保留**。实验室 ready 小幅改善（prefetch 本发生在 load 后，符合预期），真正的收益在生产端负载：每次浏览少渲染 11-17 个动态页面。**线上效果待部署后复测。** 用户可见的权衡：站内导航点击不再有预取加速——对本来就要动态渲染的页面，实际点击等待不变。

## 实验 #4：访客数据缓存（用户已批准的 A 方案）

- **假设**：三个核心页每次请求都全量查库；未登录访客的查询结果完全由内容决定，可放进 Next 数据缓存。线上 TTFB 里查询与渲染占大头，缓存后访客请求免查库。
- **改动**：新增 `src/lib/visitorContentCache.ts`（`unstable_cache` + `content` tag + 60s 兜底；**任何登录态一律直查绕过缓存**，private/草稿不进共享缓存；vitest 环境显式旁路；`next/cache` 惰性动态加载——静态引入会让 `payload run` CLI 在纯 node 环境挂起，被 `production-migration-deploy` 测试逮到）。三个页面接入；Blog/Projects 集合与 Home 全局挂 afterChange/afterDelete 失效钩子（失败仅告警，60s 兜底仍在）。
- **护栏**：tsc ✓、eslint ✓、golden check 全绿、npm test 全绿（两处失败分别由 VITEST 旁路与沙箱环境解释：nginx 探测的 mktemp 与 canary 的 tsx socket 均为沙箱拦截，沙箱外全过；production-migration-deploy 满载偶发 30s 超时，单独重跑 7/7 通过）。
- **测量**（15 次 fast4g）：文章能用 p75 281→**266.8**；首页/列表持平。**热 TTFB：首页 36→7-12ms，文章 ~200→17-35ms。** 棘轮全绿。
- **结论**：**保留**。实验室 ready 变化小（墙在浏览器绘制），价值在生产端查询消除与负载削减。**线上效果待部署后复测。** 注意：Markdown 渲染仍是每请求执行（渲染级缓存属 B 方案，未做）。
