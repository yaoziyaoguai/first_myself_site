“任务已经成功了，为什么报表还没有数据？”这个问题足以说明，只统计成功和失败，并不能完整描述数据服务的健康状况。

一次任务可能先失败后重跑成功，最后按时交付；也可能所有节点都显示成功，却没有写入消费者需要的分区。质量检查被终止与真正的生产节点失败，对产出状态的影响也不相同。把这些情形压成一个成功率，会得到一个容易展示、却很难指导恢复的数字。

健康度治理要回答的是：某个被期待的交付，在约定时间是否满足了使用条件；如果没有，影响哪些对象，应该恢复哪一段链路，恢复后怎样证明问题已经解除。执行日志是重要证据，但交付约定、依赖关系和验证方式同样不可缺少。

本文使用合成的批处理案例讨论这一问题，不披露实际任务、状态编码或业务统计。提出的数据契约和恢复控制属于建议设计，不意味着现有平台已经提供了这些能力。

## 一、先定义交付，再定义健康指标

一个可验证的交付至少需要说清：哪个数据对象、哪个业务时间范围、什么时候可用、什么条件下算可用，以及谁需要它。只写“每天运行成功”，仍然没有明确交付的业务日期、完整性和可读取状态。

可以把一项简化约定写成：某汇总数据的业务日 D 分区，在 D+1 日 10:00 前，对指定消费者可读取，关键字段满足约定类型，业务键不重复，必要输入范围已覆盖，出现异常时由明确联系人处理。这里的具体检查应由数据用途决定，不是所有表都机械使用同一套阈值。

数据契约的价值在于把这些约定显式化。公开的 Open Data Contract Standard 包含结构、质量、支持、角色与服务约定等内容，可以作为检查遗漏的参考；采用其思想不意味着必须引入完整的新平台或宣称已经符合该标准。[ODCS：Definition](https://bitol-io.github.io/open-data-contract-standard/latest/)

从治理角度看，契约还回答谁有权改变约定。调整字段语义、缩小历史范围或延后可用时间，可能不影响 SQL 能否执行，却会影响消费者。技术上向后兼容，不等于业务语义不变；变更流程应按实际影响区分通知、协商与批准要求。

同一份数据也可能服务不同消费者。低时效探索可以接受隔日更新，关键交付不能接受。此时一个笼统的“健康”标签会遮蔽差异，更合适的是保留服务约定或消费场景，让指标回到具体对象。暂时拿不到消费约定时，可以先展示运行健康，但应明确它不是完整的数据交付可靠性。

## 二、执行成功、数据就绪与消费者可用是三个时点

设一个合成任务的计划时刻为 09:00，交付期限为 10:00。首次尝试在 09:10 失败，后续尝试在 09:45 正常成功，写入提交完成于 09:47，质量检查通过于 09:49。直到 10:05，消费者侧的发布状态和可读探测才确认该版本可用。

如果交付约定以消费者可用为准，这次交付晚了五分钟。不能因为执行在 09:45 成功，就写成准时完成。反过来，若只是看到消费者第一次查询发生在 10:05，也不能据此证明数据到 10:05 才可用。第一次使用是行为事件，可用状态需要另外的发布记录或探测证据。

![从首次失败、重跑成功、写入提交到消费者侧可用的时间线。](https://wangjinkun333.me/api/media/file/governance-longform-03-reliability-recovery-delivery-timeline-1dabf8acb6e8-d24d45105f80.jpg)

图 1：合成案例中的 10:05 是可用确认时刻，不是首次查询时刻。各阶段用不同证据确认，避免把运行成功直接当成对外可用。

可用探测本身也可能有采样间隔。如果上一次探测 09:59 不可用、下一次 10:05 可用，只能说转换发生在这个区间内，不能精确宣称延迟五分钟。上图为已知发布生效时刻的教学场景；真实系统应记录时间精度和来源，避免把采样误差隐藏在秒级时间戳里。

Google SRE 对数据处理流水线的讨论把端到端延迟、正确性和处理过程放在一起，而不是只看单个任务状态。批处理健康治理也应保留这种端到端视角：执行成功可以支持运行恢复判断，数据是否满足消费者约定还需要其他检查。[Google SRE：Data Processing Pipelines](https://sre.google/sre-book/data-processing-pipelines/)

质量节点和依赖检查节点的角色因此需要单独标注。依赖检查成功只说明其检查条件满足；质量检查被强制跳过不等于质量合格；生产节点正常成功也不能替代业务范围核对。把节点角色分开，既能避免把检查异常误认为完全没有生产，也能避免把检查未通过隐藏在总体成功里。

## 三、计划、尝试与观测需要分别建模

可靠性统计通常涉及三层对象。计划表示本来期待完成的一次交付；尝试表示为了完成它而发生的一次执行；观测表示系统在某个时点记录到的状态。一次计划可以有多次尝试，一次尝试也可以有多个观测版本。

这个区别首先决定分母。一次计划失败三次、第四次成功，如果统计执行成功率是 1/4；如果它仍在期限内完成，交付结果可能是一次准时成功。前者适合研究恢复成本与运行稳定性，后者适合描述使用者收到服务的情况。两个数字可以同时存在，不必互相否定。

计划身份也不能只用自然日期。小时任务一天有多次计划，跨天任务实际开始日期又可能不同于业务日期。可靠的键应来自源系统的计划标识或明确的原始计划时刻，并带上任务、环境等身份边界。仅凭任务名相同、开始时间接近，就合并成一次重试，可能把两个正常计划错误归为同一组。

对于重跑，只有能确认它对应同一个原计划时刻，且触发类型与源系统语义允许关联时，才把它纳入该计划的观察组。无法确认的补数、临时执行或独立重跑，应隔离保留，既不丢弃成本，也不强行改变某个计划的成功状态。

观测版本的选择同样需要明确。先按失败状态过滤，再对实例取最新，得到的永远是“最新失败记录”，而不是实例最新状态。应在保留完整状态集合的前提下确定最新可解释观测，再判断它是什么状态。若来源只有一次终态采集，也不能想当然地认为表里一定能还原所有中间重试。

这些规则的作用是限制结论，而不是制造复杂度。来源只支持实例累计结果，就只在实例层统计；能够识别计划和尝试时，再增加恢复判断。缺少关键身份仍然强行做精细指标，只会得到看似完整的错误分类。

## 四、恢复判断必须考虑顺序、终态与观察截止

“出现过成功”不能作为唯一恢复规则。先失败后正常成功，可能表示恢复；先正常成功后又失败，可能是后续重跑失败；正常成功后强制成功或状态冲突，又需要另行解释。状态集合相同，时间顺序不同，结论可能完全不同。

对同一计划，至少应输出：观察到的正常成功、末次明确失败、人工干预、尚未结束和无法判断。可以同时保留首次失败时间、最后一次正常成功时间、末次尝试状态与恢复耗时。不要用某个数值状态的 MAX 充当“最佳状态”，状态编码大小没有这种业务含义。

恢复耗时的起止也有多个合理定义。从首次失败到最终成功，适合看这次异常持续多久；从人工介入到恢复，适合看处置过程；从交付期限到恢复，才接近消费者受到的延迟。指标名称必须写出是哪一个，不应都叫“恢复时间”。仍未恢复的对象不能把耗时记成零，可以展示截至观察时点的已持续时长，并标记右侧尚未结束。

每日快照还引入了观察截止。D 日生成的结果只能代表当时已经可见的记录，D+1 才补到的成功不能被假装为 D 日当时已知。可以选择保留原快照并发布修订版本，也可以按明确的回补策略重算历史，但两者要有版本依据。否则一张历史报表今天和明天变化了，却无法解释是恢复发生、采集补齐还是口径改变。

新节点和低频节点需要继续保护。如果观察到五个计划，就报告五个计划上的结果，不能补齐三十个自然日再把二十五天空白算失败。没有完整计划表时，未出现记录既可能是不应该运行，也可能是漏采或根本没触发；单凭运行事实无法区分。

## 五、未知结果不能从可靠性分母中消失

假设已经有一份完整的应交付计划清单，共十项，其中八项确认准时、一项确认迟到、一项无法确认。已确认准时占全部计划的 80%；即使未知项最终被证实准时，比例也最多到 90%。因此可以报告准时率在 80% 到 90% 之间，并单列一项未知。

如果只统计已知结果，会得到 8/9，约 88.9%。这个值是“结果已知的计划中的准时比例”，不等于全体准时率。未知项若集中在失败或采集异常场景，排除它还会使指标系统性偏高。

![十项应交付中八项准时、一项迟到、一项未知，对应百分之八十至九十的范围。](https://wangjinkun333.me/api/media/file/governance-longform-03-reliability-recovery-reliability-denominator-068cfceaab11-b5dfdf81c52f.jpg)

图 3：上下界需要完整的应交付集合。缺少计划分母时，不能用运行记录总数替代后再计算同样的范围。

```sql
WITH delivery AS (
  SELECT * FROM VALUES
    ('p01','ON_TIME'), ('p02','ON_TIME'), ('p03','ON_TIME'),
    ('p04','ON_TIME'), ('p05','ON_TIME'), ('p06','ON_TIME'),
    ('p07','ON_TIME'), ('p08','ON_TIME'), ('p09','LATE'),
    ('p10','UNKNOWN') AS t(plan_id, delivery_status)
), counts AS (
  SELECT COUNT(*) AS expected_count,
         SUM(CASE WHEN delivery_status='ON_TIME' THEN 1 ELSE 0 END) AS on_time,
         SUM(CASE WHEN delivery_status='UNKNOWN' THEN 1 ELSE 0 END) AS unknown_n
  FROM delivery
)
SELECT expected_count, on_time, unknown_n,
       on_time * 1.0 / expected_count AS confirmed_lower_bound,
       (on_time + unknown_n) * 1.0 / expected_count AS possible_upper_bound,
       on_time * 1.0 / (expected_count - unknown_n) AS known_only_ratio
FROM counts;
```

这个教学样例的分母为非零，生产 SQL 仍需保护无计划和全未知的情形。空集合不能默认成功率 100%，也不能默认 0%；它可能表示本周期没有约定交付，或计划来源缺失。两者需要在数据准备阶段区分。

SLO 是服务约定目标，SLI 是观察到的服务表现。Google SRE 建议围绕使用者关注的结果制定 SLO，并把指标与行动联系起来。对数据服务，可以把准时可用、完整范围或可接受质量作为不同指标，但不要未经协商给所有任务套同一个成功率目标。[Google SRE：Implementing SLOs](https://sre.google/workbook/implementing-slos/)

如果采用错误预算，也要注意低频业务的离散性。一个月只有四次交付时，一次迟到就是四分之一，百分比会剧烈波动。此时可以同时展示具体事件、连续违约和业务影响，不必强行套用适合高频请求的告警方法。未知结果则应触发补证据，而不是被消耗或返还为一个虚构预算数。

## 六、事件时间与获知时间决定历史报表怎么解释

健康报表有一个容易被低估的问题：数据什么时候发生，与治理系统什么时候知道这件事，可能不是同一个时间。忽略这一点，会让前一天的失败在今天悄悄变成成功，也会让一次确实迟到的交付因为晚到记录而被误判为准时。

设某次计划的期限是 10:00。治理在 10:10 做快照时只看到失败记录，之后在 10:30 收到一条正常成功记录，来源写明实际成功时间为 09:55。这时有两种不同的提问：“10:10 时我们掌握了什么证据”和“根据后来补齐的记录，这次执行实际何时成功”。两个答案都可以成立，但它们不能共用一个未标版本的状态。

对于第一个问题，10:10 的观察结论仍应保留为当时无法确认正常恢复。对于第二个问题，可以在新的核对版本里记录执行于 09:55 成功，同时注明这条证据在 10:30 才可见。即使执行成功早于期限，也仍需要实际提交和消费者可用证据，才能进一步判断交付是否准时。

再换一种情况：10:30 才收到的记录表明执行实际在 10:25 成功。它支持后来恢复，却不改变期限已经错过的事实。若只是用“最新状态成功”覆盖历史结论，第一次与第二次情形都会变成绿色，及时恢复与迟到恢复的差异就消失了。

| 问题 | 使用的时间 | 合理输出 |
|---|---|---|
| 某个快照当时知道什么 | 截止时点前已采集的观测 | 当时可见状态与未知项 |
| 事后重建实际运行结果 | 有效来源记录的事件时间 | 修订后的执行结果及证据版本 |
| 是否满足交付期限 | 约定期限与真实可用时间 | 准时、迟到、未交付或未知 |
| 采集是否足够及时 | 事件时间与进入治理系统的时间 | 采集延迟与覆盖，不当成交付延迟 |

这种双时间处理不一定要求引入复杂的时态数据库。最小实现可以保留事件时间、来源更新时间、采集时间、统计截止时点和规则版本，并明确历史结果是否允许回补。核心是让读者能够区分事实修订与事件本身改变，而不是追求某种数据库模型的完整形式。

还需要约定核对周期何时结束。对于会在几小时内补齐的日志，可以保留“初报”和“核定”两个阶段；对于长期无法确认的记录，则保持未知并推动来源修复。不能无限等待到所有对象看起来成功才发布结果，也不能永远用第一版失败忽略后续可靠证据。

相同道理适用于删除和迁移。一个节点今天已经下线，并不意味着它上周不应该执行；今天的维护人也未必负责上周发生的变更。用于当前联系的配置与用于解释历史行为的配置应该区分。暂时只有当前配置时，就应在报表里说明这个限制，避免把历史责任强行归到现在的联系人。

从治理运营角度看，事件账与问题账也要分离。同一代码缺陷造成五个业务日交付失败，属于五次交付事件，但可能只需要一个根因整改问题；一次事件又可能暴露多个独立缺陷。保留它们之间的关联，才能同时统计用户受到多少次影响、团队需要修复多少项根因，而不重复计算或遗漏工作。

## 七、从目标数据反查生产者，才能制定恢复顺序

当目标表不能产出，直接寻找“名字相同的任务”并不可靠。任务可能写多张表，也可能名字像表却没有写入；一个数据集也可能由多个任务或多个路径生产。恢复分析应从输入输出关系开始，区分数据对象、工作定义与具体运行。

OpenLineage 的对象模型明确区分 Dataset、Job 和 Run，并区分设计期与运行期事件。这个区分很适合用于检查现有血缘表的含义：静态关系能够帮助定位可能的生产者，运行事件才补充某次执行的实际情况。[OpenLineage：Object Model](https://openlineage.io/docs/spec/object-model/)

取一个最小链路：`raw_x → build_stage → stage_x → build_report → report_x`。如果目标是 report_x，build_report 已上线，但 build_stage 未上线，那么只开启目标任务仍然不能确保输入就绪。还需要确认 raw_x 的业务分区可用、build_stage 是否是有效生产者，以及其产出能否满足 build_report 的需要。

![通过数据输入输出关系定位中间表的实际生产节点。](https://wangjinkun333.me/api/media/file/governance-longform-03-reliability-recovery-producer-lookup-c052ace6ad7a-cec59f51fcde.jpg)

图 4：表和任务是不同对象。恢复顺序由有效依赖与实际数据就绪条件决定，不能从相似名称直接推断。

```sql
WITH lineage AS (
  SELECT * FROM VALUES
    ('build_stage', 'raw_x',   'stage_x',  'OFFLINE'),
    ('build_report','stage_x', 'report_x', 'ONLINE')
    AS t(job_id, input_dataset, output_dataset, release_state)
), target_inputs AS (
  SELECT input_dataset FROM lineage WHERE output_dataset='report_x'
)
SELECT i.input_dataset AS required_dataset,
       p.job_id AS producer_job,
       p.release_state
FROM target_inputs i
LEFT JOIN lineage p ON i.input_dataset=p.output_dataset;
```

结果给出 stage_x 的生产者 build_stage 及其下线状态。它只是待核查的恢复前提，不是“自动上线清单”。生产者是否已经由新任务替代、是否有外部输入、是否允许补历史数据，都需要进一步确认。没有匹配到生产者时，应标为未知来源，不能直接把这张表判断成已经就绪。

真实依赖可能有多条生产路径。全部上线可能重复写入，选择任意一条又可能遗漏某些分区。恢复计划必须明确哪条路径对哪个业务范围有效，并在执行前固定代码和配置版本。否则恢复过程中关系变了，原先正确的顺序也可能失效。

## 八、循环依赖要放回业务时间判断

静态表图中出现自依赖，并不总是意味着永远无法运行。一个日累计表读取前一天结果、写入当天结果，表级图上存在自环；展开到业务时间后，关系可能是 `T[D-1] → T[D]`，它可以按日期顺序推进，前提是起始状态有明确初始化方法。

真正需要警惕的是同一轮、同一业务范围的相互等待。例如 A[D] 必须等待 B[D]，B[D] 又必须等待 A[D]，且没有已经就绪的初始输入、替代路径或被明确定义的迭代算法。这种约束无法通过简单调整任务先后顺序解决。

反过来，也不能看到读取历史日期就宣布没有循环。SQL 实际可能使用当前日期参数，调度依赖可能仍绑定本轮实例，或者历史初始化也依赖当前结果。需要同时查看读写分区、参数展开和调度依赖，确认它们描述的是同一个时间关系。

依赖分析也要考虑变更影响。删除一个中间字段、改变业务日期含义或缩短保留期，可能不改变表级边，却让下游恢复失败。路径存在只是结构信息，数据契约决定这条路径能不能继续工作。影响评估应尽可能定位实际使用范围，不能把所有可达下游数量直接等同于实际受影响用户数。

## 九、恢复必须验证幂等性与发布过程

恢复经常通过补数或重跑完成，但“再运行一次”本身并不安全。若逻辑是读取目标当前累计值，再加本次增量，重复执行可能把同一增量加两次。使用覆盖写入也不自动解决问题，因为错误的新值可能已经在计算阶段形成。

可恢复的写入需要稳定输入范围和明确替换边界。例如按业务日期读取固定上游版本，重新计算该日期的目标分区，再替换对应分区；或者依据可靠业务键和版本规则做幂等合并。具体方式取决于存储系统能力，不能把某种引擎的事务特性推广到所有表格式。

同时需要避免消费者读到半完成状态。可以在系统能力允许时先写临时版本，完成数量、主键和业务校验，再发布或切换可见版本。若平台不支持原子切换，就要说明恢复窗口、暂停消费或其他保护措施，不能仅通过一条“写入成功”状态宣称发布原子性。

恢复验证应覆盖四类事实：该业务范围是否完整、关键结果是否正确、消费者是否能够读取，以及下游是否真正恢复。只检查目标分区存在，可能遗漏空分区；只检查行数相同，可能遗漏内容错位；只看到下游任务成功，又可能遗漏错误版本被传播。

还要给恢复保留退出条件。发现实际输入范围与计划不符、目标表已被其他运行修改、数据校验失败或依赖版本发生变化，应暂停继续向下游推进。恢复流程不是一次性脚本竞速，越向下游传播，错误回滚的范围通常越大。

## 十、治理优先级应来自影响，而不只是失败次数

一天失败十次、最终按时交付的非关键任务，与一个月只失败一次却阻断关键交付的任务，不能只按失败次数排序。健康度治理至少需要同时看交付影响、异常持续、恢复成本和发生频率。

这并不要求立即做一个复杂加权总分。分数如果缺少权重依据，反而会遮蔽真正的争议。可以先将对象分为确认影响交付、存在运行异常但交付未受影响、以及证据不足三类，再在每类里按持续时间和服务重要性安排处理。分类标准公开后，使用者能够反驳或补充证据，比一个不可解释的健康分更有用。

对运行侧，保留首次失败、恢复、干预和未结束状态；对交付侧，保留计划数、准时、迟到、未交付和未知；对恢复侧，保留阻塞生产者、输入范围和验证结果。三个视角可以在 BI 中互相定位，但不要因为某个视图出现绿色，就替另外两个视图作结论。

第一阶段的治理成果可以是：可靠地区分了一次异常究竟停在运行、发布、数据质量还是消费可用阶段，并能给出有依据的恢复前提。进一步接入完整计划、分区提交和消费者可用记录后，才有条件评估端到端交付可靠性。这个演进顺序比先给所有表一个看似完整的健康等级更诚实，也更容易在真实故障中发挥作用。
