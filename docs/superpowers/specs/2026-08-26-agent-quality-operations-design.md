# Agent 质量反馈与生产运维闭环设计

日期：2026-08-26

## 目标

在不把个人博客扩张成评测平台的前提下，补齐两个最小闭环：

1. 站长能在现有 Payload 后台判断文章 Agent 是否真的帮助访客，包括问了什么、是否找到证据、是否点击引用、失败原因和模型用量。
2. 生产环境每天自动检查健康状态、TLS、模型额度和备份，并通过 GitHub Actions 失败状态形成可见告警。

同时让访问统计能够识别站长自己的访问，避免把调试和日常浏览误算成真实访客。

## 非目标

- 不建设跨文章知识库、评测平台或会话回放系统。
- 不保存 Agent 回答全文、对话历史、完整 IP、User-Agent 原文或地理位置。
- 不引入第三方统计、告警或可观测性 SaaS。
- 不自动轮换、读取或展示模型 API Key。
- 不让遥测失败影响访客正常问答。

## 已有基础

项目已经具备匿名页面访问统计、Agent 每身份与全局硬限额、token 计数、部署前 PostgreSQL/媒体备份、部署 canary、域名健康检查和 fail-closed 回滚。本次只补缺口，不建立平行链路。

## 数据设计

### Agent 查询事件

新增 `blog_agent.query_events`，每次有效文章问答最多产生一条记录：

- `query_id`：复用公开响应中的随机查询 ID，唯一索引。
- `article_slug`：当前文章 slug，不接受客户端另行指定。
- `question_excerpt`：服务端脱敏后、最多 500 字的问题摘要。
- `outcome`：`answered`、`insufficient_evidence`、`rate_limited` 或 `provider_error`。
- `cached`、`citation_ids`、`code_citation_count`：回答质量与来源信息。
- `clicked_citation_ids`：访客实际点击过的本次引用 ID，去重保存。
- `input_tokens`、`output_tokens`、`latency_ms`：供应商消耗与用户等待时间。
- `created_at`：用于 30 天保留和后台滚动窗口。

问题摘要在写库前执行固定规则脱敏，覆盖邮箱、Bearer/API Key、JWT、私钥区块、常见密码与凭据赋值；无法安全处理时保存固定占位符而不是原文。数据库不保存身份哈希，不把查询与页面访客画像关联。

30 天以前的查询事件由每日运维任务批量删除；查询写入时也做小批量兜底清理，避免定时任务短暂失效导致无限增长。

### 引用点击

新增同文章的 `POST /api/blog/[identifier]/agent/feedback`，只接受 `queryId`、固定事件名和 `citationId`。服务端验证：

- 同源请求、JSON、严格大小限制与字段白名单；
- slug、query ID、citation ID 的格式和长度；
- 查询属于当前公开文章；
- citation ID 必须存在于该次回答记录中；
- 同一引用只计一次。

客户端在文章引用或 GitHub 行号链接被点击时使用 `sendBeacon`，失败静默，不阻止跳转。

### 访问来源与站长访问

在现有 `page_views` 增加：

- `network_prefix`：IPv4 只保留 `/24`，例如 `182.92.85.*`；IPv6 只保留规范化 `/64` 前缀；无法解析时为空。
- `is_owner`：请求携带有效 Payload admin/editor 登录会话时为 `true`，否则为 `false`。

不保存完整 IP。现有 HMAC 访客哈希继续用于匿名去重和限流。后台访问概览默认排除 `is_owner=true`，提供“包含站长访问”的只读视图；访问列表显示脱敏网段和站长标记。未登录设备不会凭网段被自动认定为站长，避免共享 NAT 下误判。

页面访问记录保留 30 天。每日任务批量删除过期记录；后台所有汇总继续按滚动时间窗口查询。

## 后台体验

复用“运营 → 访问统计”页面，在现有访问概览下增加“文章 Agent · 近 7 天”：

- 提问数、回答率、证据不足率、失败/限流数；
- cache 命中率、引用点击率、代码引用次数；
- 输入/输出 token、今日请求数与全局日限额占比；
- 最近证据不足或失败的问题摘要、所属文章和原因。

后台默认不展示成功回答的逐条问题，降低噪声；只有证据不足和失败问题进入“待改进”列表。所有内容只对 admin/editor 可见。

## 记录位置与失败语义

`BlogAgentService` 在产生最终结果的同一服务边界记录查询事件，复用现有 repository 注入方式。遥测写入采用 best-effort：数据库写入失败只记固定错误码，不改变已生成的回答、HTTP 状态或引用。

供应商 token 由现有 usage policy 记录；查询事件同时保存本次 token，便于按文章分析。cache 命中时 token 为 0。路由级无效请求、跨站请求、404 和未开启的 Agent 不记录问题内容。

## 生产运维

新增独立的 GitHub Actions 定时工作流，支持 `schedule` 和手动触发，复用现有 SSH Secrets，不引入新凭据。每天执行：

1. 运行公网 `/api/health`、容器健康和磁盘检查。
2. 检查 TLS 剩余有效期不少于 21 天。
3. 创建 PostgreSQL 与媒体备份，保留最近 7 份。
4. 对数据库 dump、媒体压缩包和最终归档执行可读性检查。
5. 清理 30 天以前的页面访问和 Agent 查询事件。
6. 读取当天 Agent 请求数与 token；达到全局日限额的 80% 时任务失败，硬限额仍由在线请求路径执行。

任一步失败都让 workflow 失败，从而利用 GitHub Actions 自带通知和红色状态形成告警。任务互斥运行，不能与生产部署同时操作备份。日志只输出计数、阶段码和文件名，不输出数据库 URL、问题原文、IP、Key 或供应商响应。

`scripts/health-check.sh` 的 TLS 阈值改为可配置且默认 21 天。`scripts/backup.sh` 在原子移动最终文件前验证 dump 与 tar；验证失败不会留下看似成功的正式备份。

API Key 轮换继续由供应商控制台和 GitHub Secrets 完成。运维文档增加季度轮换步骤：创建专用低额度 Key、更新 Secret、触发部署与 canary、确认成功后吊销旧 Key。代码不读取 Secret 当前值。

## 安全与隐私边界

- 所有问题摘要和网络段只存服务端 PostgreSQL，不能通过匿名 API 查询。
- 新 feedback API 不接受自由文本，不返回查询是否存在的可枚举细节。
- 后台 SQL 使用参数绑定；问题与 slug 不拼接进 SQL。
- 迁移只新增表和 nullable/defaulted 列，与上一版应用向后兼容，保证镜像回滚安全。
- 生产迁移失败时继续沿用现有 fail-closed 回滚流程。
- 30 天保留是强制上限，不提供永久保存开关。

## 测试与验收

实现遵循 red-green-refactor：先写失败测试，再写最小代码。自动化覆盖：

- 凭据、邮箱、JWT、私钥和超长问题脱敏；
- answered、证据不足、限流、provider 失败与 cache 命中的事件记录；
- 遥测数据库故障不破坏正常回答；
- feedback 严格输入、文章隔离、引用白名单和点击去重；
- IPv4/IPv6 脱敏、可信代理取址和 Payload 登录身份识别；
- 后台汇总默认排除站长访问，token/比例计算和 30 天清理；
- migration up/down、上一版兼容性；
- 备份验证失败、TLS 阈值、额度 80% 告警和定时 workflow 的 fail-closed 顺序。

上线前运行完整测试、ESLint、TypeScript、production build、安全审查和 PR CI。合并后由正常 GitHub 链路部署阿里云；生产验收检查后台数据、一次安全测试问答、引用点击、站长访问标记、健康/TLS 和定时工作流手动执行。测试问题只使用公开文章内容，不提交凭据或个人数据。

## 完成标准

- 后台能回答“最近哪些问题没答好、为什么、是否有人点击依据、用了多少 token”。
- 后台能默认排除已登录站长访问，并显示访客脱敏网段。
- 过期页面访问和问题摘要不会超过 30 天。
- 每日 workflow 能验证健康、TLS、备份、清理和额度，并在异常时明确失败。
- 所有新增遥测和运维失败均不会泄露 Secret，也不会让公开问答返回错误数据。
